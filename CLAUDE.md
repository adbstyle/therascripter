## Shell Commands

- Never put `#` comments inside Bash tool calls — write explanations as plain text before the tool call instead. Comments at the start of a command block break allow-list pattern matching.

## Project Summary

Therascript is an Electron-based macOS desktop app for local therapy session transcription and anonymization. All processing happens on-device (no cloud). German + Swiss-German dialect support. Targets Apple Silicon Macs (M1-M4). The currently shipped builds require macOS 26 (Tahoe) or newer because the bundled `libggml-metal.0.dylib` (whisper.cpp Metal backend, copied from the Homebrew `whisper-cpp` bottle by `scripts/setup-whisper.sh` on a macOS-26 host) is linked against the macOS-26 SDK with `minos 26.0` and references the `MTLResidencySetDescriptor` symbol. Lowering the floor is tracked as Issue #97. Pyannote is NOT the cause — the Python sidecar does not depend on `libggml-metal`.

Key docs: `docs/product/` (living product documentation — architecture, features, operations, ADRs). Historical planning docs archived in `docs/archive/`.

## Clean-Machine-Testing (Test-Tiers)

Dev-Macs maskieren Endnutzer-Fehler (Homebrew-Fallbacks, `~/.flair`, `~/.cache/huggingface`, volle Shell-Env). Drei Tiers:

1. **Jeder Release (automatisch):** `release.sh` baut zuerst, dann `verify-bundles.sh --app dist/mac-arm64/Therascript.app --smoke` — erst bei Grün wird getaggt/gepusht/released.
2. **Vor grösseren Releases (manuell, ~15 min):** `scripts/sim-clean-install.sh A` → DMG installieren → `scripts/sim-clean-install.sh --launch-clean` → FirstLaunchScreen, Modell-Download, eine volle Pipeline → `--restore`.
3. **Nur wenn Tier 1–2 einen User-Report nicht erklären:** frische macOS-VM (z. B. UTM/Tart).

Dev-Läufe mit dem ausgelieferten Python-Interpreter: `THERASCRIPT_USE_STANDALONE=1 npm run dev` (sonst bevorzugt Dev das venv, und Prune-Fehler im Standalone-Build bleiben unsichtbar).

## Architecture

**Build tooling:** electron-vite (Vite-based) with React plugin + Tailwind CSS v4 plugin.

**Three Electron processes:**
- **Main** (`src/main/`) — App lifecycle, window creation, CSP injection, IPC handlers. Security-hardened: navigation blocked, popups denied, sandbox enabled.
- **Preload** (`src/preload/`) — Context bridge exposing APIs to renderer. All IPC channels use Zod schema validation (schemas in `src/shared/validation/`).
- **Renderer** (`src/renderer/`) — React 19 + Tailwind CSS UI. Path alias: `@renderer` → `src/renderer/src`.

**Shared** (`src/shared/`) — Types and Zod validation schemas used by both main and renderer processes.

**ML pipeline — Audio** (strictly sequential, one model at a time, **diarization-first since Issue #78 / ADR-007**):
1. Python sidecar — pyannote.audio diarization via auswählbares Modell aus Katalog (Default: `speaker-diarization-3.1`; optional: `speaker-diarization-community-1` für bessere Deutsch-Performance). Active model stored in electron-store (`activeModels.diarization`), verwaltet via Settings → Modelle. HF_HUB_OFFLINE=1 erzwingt lokale Cache-Nutzung. ✓ implemented
2. PCM-Byte-Stitching — Stitch aller Pyannote-Speech-Segmente mit ±200 ms Padding zu einer kontinuierlichen WAV (`AudioStitchService.stitchPcmSegments`, direkte Byte-Range-Konkatenation in Node, kein ffmpeg mehr; Payload gegen ffmpeg golden-verifiziert byte-identisch). Implicit step within whisper executor; eliminates silence from whisper input → strukturell halluzinations-frei. ✓ implemented
3. whisper.cpp subprocess — ASR auf der gestitchten WAV (single subprocess call) via auswählbares Modell aus Katalog (Default: Whisper Large V3 Turbo Q5_0 multilingual; optional: Swiss-German-Fine-Tune). Output-Timestamps werden über persistierte StitchMap (`src/main/ml/timestamp-remap.ts`) auf Original-Wall-Clock zurückgemappt. Active model stored in electron-store (`activeModels.transcription`), verwaltet via Settings → Modelle. ✓ implemented
4. Python sidecar — flair NER (flair/ner-german-large) + Regex + Blocklist → TipTap document ✓ implemented
5. llama.cpp subprocess — optionale Zusammenfassung über auswählbares Modell aus Katalog (Default: Gemma 3 4B Instruct Q4_K_M GGUF). Registriert als letzter Schritt beider Pipeline-Chains (Audio + PDF). Wenn Modell nicht installiert → Executor skippt den Step geräuschlos, Summary bleibt NULL. Active model in electron-store (`activeModels.summarization`), verwaltet via Settings → Modelle. Anders als ASR/Diarization darf der aktive Summarization-Slot leer sein (deaktivieren + löschen erlaubt → Pipeline skippt den Step). ✓ implemented

**ML pipeline — PDF** (extraction → ocr → anonymization → summarization):
1. pdfjs-dist — Text extraction per page (with `standardFontDataUrl` configured) ✓ implemented
2. Swift CLI helper — Apple Vision OCR for scanned pages (skipped if all text) ✓ implemented
3. Python sidecar — flair NER + Regex + Blocklist → TipTap document (shared with audio) ✓ implemented
4. llama.cpp subprocess — optional summarization (shared with audio). ✓ implemented

**ML models:** Stored in `~/.therascript/models/<type>/` (e.g. `models/asr/`, `models/diarization/`, `models/ner/`). Required-group dirs are bootstrapped at startup by `initDatabase()`; optional-group dirs (e.g. `models/summarization/`) are created on-demand by `downloadSingleModel` — only existing once the user actually downloads an optional model.

**First launch:** FirstLaunchScreen checks for models, validates disk space (5 GB minimum — deckt Download plus Entpacken; seit Artefakt v3 entsteht keine Fast-Kopie mehr, README und Installationsanleitung nennen deshalb ~5 GB), downloads ~1.7 GB (Whisper 0.6 GB + Pyannote 0.06 GB + flair NER 1.0 GB, Werte aus `src/shared/model-catalog.ts`) with progress tracking. Models persist across app updates.

**Python sidecar:** Two modes: (1) **Dev**: Python venv at `python_sidecar/venv/` — one-time setup after fresh clone: `scripts/setup-pyannote.sh --model` then `scripts/setup-ner.sh --model`. (2) **Production**: Standalone relocatable Python at `python_sidecar/standalone/` built via `uv` (no PyInstaller, no hidden import issues). Build with `npm run sidecar:build`. The torchcodec shim (`torchcodec_shim.py`) is loaded via `sitecustomize.py` in the standalone environment. Pyannote requires HuggingFace token (`huggingface-cli login`) and accepted terms for `pyannote/speaker-diarization-3.1` + `pyannote/speaker-diarization-community-1`. The venv and models persist across builds — no re-setup needed for `npm run dev/build`.

**Review Editor extensions:** 3 custom TipTap node extensions in `src/renderer/src/extensions/` — `placeholderChip` (anonymized entity chips), `speakerLabel` (speaker diarization labels), `timestamp` (time markers). Corresponding NodeViews in `components/editor/`.

**Storage:** better-sqlite3 (sessions, blocklist) + electron-store (settings).

**System tray:** TrayService provides macOS menu bar icon with stop-recording action. App keeps running in background when window is closed.

**PDF import:** Drag-and-drop or button in SessionDashboard. Files copied to `~/.therascript/pdf/`. Import guard prevents duplicate imports. Copy failure triggers session rollback. Orphaned sessions (stuck in processing with no tasks) are recovered at startup.

**UI navigation:** Simple view state (`'sessions' | 'settings' | 'review'`) in App.tsx — no router. Persistent shell components live in `src/renderer/src/components/shell/`: `TitleBar` (centered wordmark, hiddenInset drag region), `BottomNav` (chip-style nav, replaces the earlier sidebar; hidden only in review) and `RecordingBar` (slim red status strip below the TitleBar, shown while recording in every view except the sessions list). The Sessions view header is labeled "Transkriptionen" in UI copy (data model term remains "session"). First-launch screen is shown conditionally via `modelsReady` state (not a view). `ModelUpdateScreen` is shown when pending model updates exist after restart (`pendingUpdates` state). `UpdateBanner` overlays the main app when new model versions are available (non-blocking). Settings view uses a master-detail pattern: a list of section cards (Sperrliste/Darstellung/Modelle/Über) drills into per-section sub-pages with a back link. Review editor opened by clicking a session card in `review` status. **Recording is a status, not a mode:** there is no fullscreen RecordingView anymore — the session card with status `recording` renders as `RecordingSessionCard` (live timer, compact VU meter, stop button) and the app stays fully navigable during recording (incl. Review editing and Settings). Only a second recording and the model-update restart remain blocked; the task queue pauses while recording (see Gotchas). First-launch screen shown when models are not yet downloaded.

**Theme system:** `ThemeContext` + `ThemeProvider` (`src/renderer/src/contexts/ThemeContext.tsx`) manage light/dark/system preference, persisted via electron-store. `createWindow()` reads `nativeTheme` to set `backgroundColor` on the `BrowserWindow` (prevents white flash in dark mode). `AppearanceSettings.tsx` renders the user-facing toggle in the Darstellung sub-page.

**ConsentBanner:** Shown above the sessions list while a recording is active — one-time reminder to obtain patient consent. Permanent opt-out via electron-store (`consentReminderShown`); dismissal without opt-out is tracked per recording in `App.tsx` (the banner unmounts on view switches and must not reappear on return).

**Icons:** `lucide-react` for all UI icons. Direct named imports (`import { Mic } from 'lucide-react'`) — tree-shakeable. Sizing via Tailwind (`h-4 w-4` inline, `h-5 w-5` standalone, `h-7 w-7` settings cards). Color via `currentColor` / Tailwind text utilities (`text-text-tertiary`, `text-primary`, etc.). `strokeWidth` should match the visual weight of surrounding text — typical values: `1.5` for large decorative icons (`h-7`, Settings cards), `1.75` for header/card icons sitting next to bold text (`h-5`), `2` for inline UI alongside a text label, `2.5` for success-checkmark emphasis. Always `aria-hidden` when decorative. **Never** use emojis as icons or hand-roll inline SVGs for new UI — exception: `AppLogo.tsx` (brand mark with multi-color paths, not a generic icon).

**Update System (Iteration 17+18):** `UpdateCheckService` checks R2 manifest for newer model versions and app updates in a single fetch. Model updates download atomically into a staging directory and swap on restart. App updates show a non-blocking sidebar hint + About page button that opens GitHub Releases. `model-update-handlers.ts` exposes model update IPC channels; `app-update-handlers.ts` exposes `appUpdate.getStatus()`, `appUpdate.check()`, `appUpdate.openReleasePage()`. Cached app update status persisted in electron-store.

**Key constraints:**
- 8 GB minimum RAM budget (~3.5 GB process peak incl. GPU memory during flair NER on 8-GB Macs — see NER-RAM gotcha)
- Production CSP: `connect-src 'none'` (zero network access)
- Context isolation + sandbox always enabled
- All ML models must be swappable (plugin architecture, NFR-9/10)
- Electron Fuses hardened at build time (RunAsNode disabled, OnlyLoadAppFromAsar, cookie encryption)
- FileVault check at startup — warns user if disk encryption is not enabled

## Gotchas

- **Alle gebundelten Dateien brauchen das Owner-Write-Bit (u+w).** Homebrew-Bottles shippen Mach-Os teils mit Modus 444/555; `cp` in den Setup-Skripten übernimmt den Modus, electron-builder packt ihn unverändert ins DMG. Auf Endnutzer-Macs schlägt dann die Gatekeeper-Anleitung `xattr -cr` mit `[Errno 13] Permission denied` fehl (xattr braucht Write-Permission — Ownership reicht NICHT), die Quarantäne bleibt auf genau diesen Dateien und Gatekeeper killt das ad-hoc-signierte Binary beim Spawn per SIGKILL (exit 137, stdout/stderr leer) — bei llama-cli endet das als stiller Summarization-Skip. Auf Dev-Macs unsichtbar (nichts ist quarantänisiert). Drei Schichten: Setup-Skripte chmod-en nach dem Kopieren, `afterPack.js` chmod-t die ganze gepackte App (Chokepoint), `verify-bundles.sh` failt bei Pfaden ohne u+w. `Rechtsklick → Öffnen` ist KEIN Ersatz für `xattr -cr` — es whitelistet nur den App-Start, nicht die inneren Binaries.
- **whisper.cpp und llama.cpp linken gegen inkompatible ggml-Generationen.** Homebrew's `whisper-cpp` baut gegen ggml ~0.9.x, `llama.cpp` gegen ggml ~0.10+/0.12+. Beide Binaries bundlen via `LC_RPATH=@loader_path/../lib`. Sie liegen deshalb in **getrennten Self-Contained-Bundles** unter `resources/whisper/{bin,lib}/` und `resources/llama/{bin,lib}/` — jedes Tool lädt seine eigene libggml-Version. Nie auf eine gemeinsame `resources/lib/` zurückgehen: das zweite Setup-Skript würde die libggml-Generation des ersten überschreiben und das ältere Binary crasht beim Modell-Init in `make_buft_list` (ABI-Mismatch, `exit code null` via Native-Signal). Für **DMG-Portabilität auf Endnutzer-Macs ohne Homebrew** ist das Setup deutlich invasiver als ein simpler `cp`: (a) jeder bundled Mach-O wird via `install_name_tool` auf `@rpath` umgeschrieben (shared Helper `scripts/lib/rewrite-macho.sh`, von beiden Skripten gesourct — scant `otool -L`-Output und rewrited jede absolute `/opt/homebrew`-Ref), (b) `libssl.3.dylib` + `libcrypto.3.dylib` aus `openssl@3` werden in das llama-Bundle mitkopiert (transitive Dep von `libllama-common`; macOS hat kein system-libssl mehr), (c) ggml 0.10+ verwendet eine Plugin-Architektur — `libggml.0.dylib` macht zur Laufzeit `dlopen` auf separate Backend-`.so` Files (Metal/BLAS/CPU-Variante pro Apple-Silicon-Generation). Die Plugins werden aus `$(brew --prefix ggml)/libexec/*.so` ins llama-Bundle mitkopiert; (d) `libggml-cpu-apple_m*.so` linkt `libomp.dylib` → auch gebundlet. (e) Die Backend-Plugins (`libggml-*.so`) MÜSSEN neben der **Executable** liegen (`resources/llama/bin/`): ggml scannt beim Backend-Load das Executable-Verzeichnis. Zwei verführerische Alternativen sind auf Endnutzer-Macs TOT: der hardcodete Fallback `/opt/homebrew/Cellar/ggml/<ver>/libexec` existiert dort nicht, und `GGML_BACKEND_PATH` wird von dieser ggml-Generation als EINZELNE Datei ge-dlopen-t (kein Suchverzeichnis) — selbst eine einzelne .so reicht nie (Metal UND CPU-Backend nötig, `make_cpu_buft_list`). Auf Dev-Macs maskiert der Cellar-Fallback jeden Fehler in diesem Layout — testen heisst: `scripts/smoke-packaged.sh` (sandbox-exec blendet /opt/homebrew aus; die 1-Token-Generation erzwingt `make_cpu_buft_list` und damit den echten Plugin-Load — `--list-devices` allein zeigt fehlende CPU-Plugins NICHT, Exit bleibt 0 bei leerer Device-Liste). Alle `install_name_tool`-Aufrufe laufen **vor** dem ad-hoc-codesign-Schritt, damit der re-sign die modifizierten Mach-Os mit-deckt. `scripts/verify-bundles.sh` prüft als CI-Smoke, dass beide Bundles null `/opt/homebrew`-Refs enthalten und alle Plugins vorhanden sind. vision-ocr bleibt in `resources/bin/` (keine shared deps, nur System-Frameworks); ffmpeg wurde entfernt — Stitching ist seit dem PCM-Byte-Umbau reine Node-I/O.
- **better-sqlite3 native rebuild:** `postinstall` and `predev` run `electron-rebuild` (for Electron ABI), while `pretest`/`pretest:watch` run `npm rebuild` (for system Node.js ABI). The `package` script runs `electron-rebuild` explicitly before building; `npmRebuild: false` in `electron-builder.yml` prevents electron-builder's own unreliable rebuild. If native module errors occur, run `npm run postinstall` manually.
- **`npm test` requires Xcode Command-Line Tools:** the `pretest`/`pretest:watch` hook calls `npm rebuild better-sqlite3` against the system Node ABI. On a fresh Mac without Xcode CLT, this fails with `gyp: No Xcode or CLT version detected!`. Fix: install once with `xcode-select --install`. Workaround if you can't install CLT but want to run tests: `npx vitest run <path>` skips the pretest hook entirely — fine for tests that don't touch SQLite (e.g. pure modules like `timestamp-remap`, `AudioStitchService.computeStitchMap`, `ProcessWatchdog`). Tests using `getDatabase()` need the rebuilt native binding to load.
- **`env -u ELECTRON_RUN_AS_NODE`:** The `dev` script unsets this env var because Electron Fuses disable RunAsNode — without this workaround, `electron-vite dev` fails.
- **`.env` file:** Contains Cloudflare R2 credentials for model uploads. Gitignored — never commit.
- **Vitest setup:** Requires `tests/setup.ts` (jsdom environment). Referenced in `vitest.config.ts`. Pool ist `forks`, **nicht** `threads` — better-sqlite3 segfaultet beim Teardown von worker_threads sporadisch (Exit 139 ohne einen einzigen fehlgeschlagenen Test, ~20 % der Läufe). Nicht für die ~2.5 s Ersparnis zurückwechseln.
- **Code signing:** No Apple Developer account — `identity: null` in `electron-builder.yml` disables electron-builder signing. `afterPack.js` flips Electron Fuses and must use `resetAdHocDarwinSignature: true` to re-sign with ad-hoc signature (`codesign --sign -`). Without this, ARM64 macOS kills the app on launch (`CODESIGNING, Code 2 Invalid Page`). Users must right-click → Open on first launch.
- **electron-vite externals:** `electron-store` (main) and `@electron-toolkit/preload` (preload) are excluded from `externalizeDeps` in `electron.vite.config.ts` — they must be bundled, not externalized.
- **Model hash sync — der Katalog ist die Quelle, das Manifest folgt ihm.** `src/shared/model-catalog.ts` (url, `sha256`, `sizeBytes`) ist die Wahrheit für First-Launch-Downloads UND für das Manifest: `release.sh` veröffentlicht am Ende `publish-manifest.sh --from-catalog`, das die Modell-Einträge aus dem Katalog der released App baut. Nach dem Upload eines neuen Artefakts deshalb die Werte des HOCHGELADENEN Objekts in den Katalog eintragen (Packaging-Skripte drucken sie, gegen das CDN prüfen) — nie umgekehrt aus einem lokal erzeugten `manifest.json` übernehmen: ein Voll-Lauf von `package-models.sh` erzeugt neue gzip-Zeitstempel und damit Hashes, die R2 nicht hat. Das neue Artefakt muss VOR dem Release auf R2 liegen; `manifest-from-catalog.ts` bricht sonst ab (HEAD + Content-Length gegen `sizeBytes`). `--app-version-only` reicht nach einem neuen Artefakt NICHT (vorher der Release-Standard): das Manifest zeigte weiter aufs alte, und frische Installationen bekämen ein "Update" zurück darauf angeboten, weil der Update-Trigger ein reiner sha-Vergleich ist. Falsche Katalog-Hashes brechen First-Launch-Downloads.
- **Standalone Python sidecar:** Built via `uv` with python-build-standalone (~1 GB). All `.dylib`/`.so` files are ad-hoc codesigned during build. If the sidecar fails to run, try `scripts/build-sidecar.sh --clean` for a fresh build. The `torchcodec_shim.py` provides a soundfile-based fallback for torchcodec (required by pyannote.audio 4.0.4+), loaded automatically via `sitecustomize.py`. **Important:** `requirements.txt` + `requirements-ner.txt` are the sole dependency source — any Python package needed at runtime (including transitive deps like `soundfile`) must be listed explicitly, unlike the old PyInstaller build which had hidden imports.
- **Gemma 4 E4B GGUF source:** No official Google GGUF for Gemma 4 E4B existed when the summarization feature shipped. Default catalog entry uses bartowski's Gemma 3 4B Instruct Q4_K_M as fallback. The repo is HuggingFace-gated — `huggingface-cli login` is required before `scripts/setup-llama.sh --model`. If/when a Gemma 4 E4B GGUF lands upstream, swap the URL/filename in `MODEL_DEFINITIONS` and re-run `scripts/publish-manifest.sh` to mirror into R2.
- **llama-cli timeouts:** `LlamaSummarizer.summarize()` provides no fine-grained progress callbacks. Zwei Grenzen greifen: `runSubprocess`-Timeout 540 s in `LlamaSummarizer.ts` (endet als Graceful-Skip) und darüber die `summarization: 600_000`-Watchdog-Wall in `ProcessWatchdog.ts` (endet als Abort). Die 540 s absichtlich UNTER der Wall halten.
- **Der ProcessWatchdog misst Liveness, nicht Fortschritt — lange progress-freie Phasen brauchen einen `[HEARTBEAT]`.** `ProcessWatchdog` kannte ursprünglich nur `onProgress` als Lebenszeichen. `ner_service.py` meldete zwischen `[PROGRESS] 10` (nach `import flair`) und `[PROGRESS] 25` (nach `Classifier.load`) nichts — dazwischen liegt der Load von 2.24 GB `pytorch_model.bin`. Auf einer 8-GB-Maschine mit vollem Swap ist das fast reiner I/O-Wait (gemessen: 281 s wall / 42 s CPU) und lag damit weit über `STALL_THRESHOLDS.anonymization = 120_000` → `controller.abort()` killte die Prozessgruppe mitten im gesunden Modell-Load, sichtbar als `Fehler — „Verarbeitung reagiert nicht mehr"` bei Task-Progress exakt `0.095` (= `0.05 + 0.10 * 0.45`). Retry konnte nie gewinnen: jeder Versuch lädt kalt. Auf Dev-Macs mit freiem RAM unsichtbar. Fix: `ner_service.py` startet über den `heartbeat()`-Contextmanager einen Daemon-Thread, der alle 10 s `[HEARTBEAT]` auf stderr schreibt; `AnonymizationService.parseNerStderrLine()` übersetzt das in `runtime.heartbeat()` (→ `watchdog.heartbeat()`) **ohne** den Progress-Wert zu bewegen. Merksätze für neue/geänderte Sidecar-Steps: (a) jede Phase ohne `[PROGRESS]` muss vom Heartbeat überdeckt sein — beim NER auch die Inferenz, denn ein 1-seitiges PDF ergibt EIN Segment und damit einen einzigen Batch ohne Zwischenmeldung; (b) **jede** stderr-Ausgabe muss durch `_emit()` (auch Fehlermeldungen und der flair-Logger via `_EmitHandler`) — ein einzelner `write()` unter Lock, weil `print()` Text und Newline getrennt schreibt und die Zeilen zweier Threads sonst verschränken; der Lock wird dabei mit Timeout genommen und im Zweifel übersprungen, weil `heartbeat()` seinen Thread nach `join(timeout=1)` aufgeben kann, während der noch den Lock hält — ein blockierendes `with` hinge dort für immer; (c) mit Heartbeat ist die Stall-Schwelle kein Zeitlimit mehr — die einzige harte Wall ist das `runSubprocess`-Timeout (NER: 900 s). `diarize.py` hat denselben Umbau (Lücke `[PROGRESS] 5` → `20` über `Pipeline.from_pretrained`, plus die Audio-Dekodierung vor dem ersten `ProgressHook`-Call); der TS-seitige Parser liegt für beide Sidecars in `src/main/ml/sidecar-stderr.ts`. - **NER-Speicher skaliert mit Zeilen × padded_len² pro Forward-Pass, nicht mit der Segmentanzahl.** flair padded jede Mini-Batch aufs längste Element und fenstert Segmente >512 Subtokens vorher in überlappende 512er-Zeilen (stride 256) — die Attention-Matrizen eines Passes kosten also ungefähr `Zeilen × padded_len²`, unabhängig davon, wie viele Segmente in der Batch stecken. Audio (viele kurze Diarization-Segmente, padded_len ~64) war deshalb nie betroffen; **seitengrosse PDF-Segmente** (ein Segment pro Seite, gebaut von `pdf-transcript-builder`, 1900–3800 Zeichen = 1–3 volle 512er-Zeilen) rissen mit der festen Batch-Grösse 32 (Regression `ad9c716`, v0.8.5–v0.8.8) das MPS-Ceiling auf 8-GB-Macs: gemessen 14.07 GiB Live-Peak bei 11 Seiten à 2800 Zeichen gegen ein Ceiling von 9.07 GiB (`1.7 × ⅔ × RAM`). Fix in `ner_service.py`: `pack_by_budget` packt Batches nach `TOKEN_BUDGET = 4096` gepaddeten Token-Slots (Deckel `MAX_SENTENCES_PER_BATCH = 32`, auf Macs mit ≤ 8 GB RAM 8 — siehe fp16-Gotcha) — gemessen (noch fp32) 3.16 GiB Live-Peak über den ganzen Lauf (5.32 GiB für einen isolierten 8×512-Pass), Audio behält oberhalb von 8 GB RAM faktisch seine 32er-Gruppen und damit den `ad9c716`-Speedup; dazu ein CPU-Fallback, wenn MPS trotzdem OOM wirft. Die Slot-Zählung UNTERschätzt leicht (flair tokenisiert intern über die Wortliste und hängt als FLERT-Modell ±64 Wörter Nachbar-Kontext an), ein OOM bleibt also möglich — deshalb **adaptive Halbierung**: bei MPS-OOM wird das Budget halbiert (Boden `MIN_TOKEN_BUDGET = 512`) und der Rest neu gepackt, MPS bleibt aktiv; erst eine unteilbare Gruppe (ein einzelnes übergrosses Segment) geht auf CPU. Absichtlich NICHT sofort CPU: das machte den langsamsten Pfad zum Dauerzustand und riss auf swappenden 8-GB-Macs die harte 900-s-Wall in `AnonymizationService.ts`. `TOKEN_BUDGET` **nie** wieder durch eine feste Segmentanzahl ersetzen — jede Konstante, die nicht die Padding-Länge einrechnet, ist auf 8-GB-Macs seitenlängenabhängig tödlich; der Degrade-Schätzer `estimate_item` (greift, wenn flair-Interna verschoben sind) muss aus demselben Grund ÜBER-schätzen. Jeder Forward-Pass emittiert `[BATCH] sentences=N rows=R padded=L budget=B` auf stderr; der Smoke-Check `ner token budget` (`scripts/smoke-packaged.sh`) importiert `TOKEN_BUDGET` aus dem gebundelten Script und prüft daraus die Invariante plus ≥2 Forward-Pässe (eine Fest-Batch-Regression ergäbe genau einen) — das Ceiling selbst ist auf Dev-Macs (>8 GB) nicht reproduzierbar. Budget-, Pack- und Schätzverhalten lockt `src/main/ml/__tests__/ner-packing.test.ts` (spawnt System-python3; ner_service.py muss deshalb ohne flair importierbar bleiben). **Kontext-Falle:** `predict()` verkettet FLERT-Kontext nur über die ÜBERGEBENE Liste — kleinere Gruppen liessen Segmente ohne Kontext und änderten die Erkennung an Seitengrenzen. `run_ner` verkettet deshalb EINMAL dokumentweit (`Sentence.set_context_for_sentences`, überspringt bereits verkettete Sentences); gemessen speicherneutral. Nach jedem abgebrochenen Forward-Pass müssen die Sentences neu gebaut werden (halb-annotierte Objekte).
- **NER rechnet auf MPS in fp16 — Gewichte UND Aktivierungen; der Speicher entscheidet auf 8-GB-Macs über den 900-s-Timeout.** In fp32 brauchte der NER-Prozess für eine 45-min-Sitzung 9.4 GiB inkl. GPU-Speicher — mehr als der ganze RAM eines 8-GB-Macs; der Swap-Stau endete bei Usern als „Zeitüberschreitung nach 900s“, obwohl die reine Rechenzeit auf dem M5 Pro unter 15 s liegt. Drei Hebel in `ner_service.py` (Messwerte je in deren Docstrings), zusammen 9.4 → 3.5 GiB bei identischen Spans/Typen: `_half_precision_on` (Tagger während `Classifier.load` direkt als fp16 auf MPS bauen), `_release_mps_cache` nach jeder Gruppe, `max_sentences_for_ram` (≤ 8 GB RAM → 8 statt 32 Segmente pro Forward-Pass). Fallen: (a) **Speicher immer als `phys_footprint` messen** (z. B. `proc_pid_rusage`), nie als RSS — `ru_maxrss` zählt MPS-Allokationen nicht mit und sah den ganzen Fehler nicht. (b) Die MPS-Watermark-Env-Vars sind KEIN Ersatz für `empty_cache()`: die Low-Watermark (1.4 × ⅔ × RAM ≈ 7.5 GiB auf 8 GB) liegt jenseits des Swaps (nachgestellt: keine Wirkung). (c) `set_default_dtype(float16)` ist globaler Zustand — strikt auf den Load begrenzt, im `finally` zurück; auf der CPU bleibt alles fp32. (d) OOM-Reaktion NACH dem `except`-Block: solange er läuft, hält der Traceback die Aktivierungen des gescheiterten Passes auf der GPU. (e) CPU-Fallback erst `tagger.to(cpu)`, DANN `tagger.float()` — `to(cpu, float32)` castet auf der GPU und braucht dort neuen Speicher (gemessen: Exit 3 statt CPU-Lauf). Smoke-Check `ner oom fallback` drückt das MPS-Limit auf 1.6 GiB (Watermark-Faktoren aus `torch.mps.recommended_max_memory()` berechnet) und verlangt Halbierung + CPU-Wechsel + Exit 0 — auf Dev-Macs ist der Pfad sonst nie erreichbar. (f) `scripts/ner-parity.py` vergleicht ohne `--ref-cpu` nur fp16 gegen fp16; `--ref-cpu` setzt `THERASCRIPT_NER_DEVICE=cpu` (nur für Messwerkzeuge — die App-Env-Whitelist lässt die Variable nie durch): fp32 auf der CPU aus dem ORIGINAL, die Fast-Kopie wird dabei weder gelesen (bei v1/v2 ist sie seit der fp16-Inferenz selbst fp16) noch geschrieben. Verifiziert mit dem v2-Artefakt: Original-Load unter `_half_precision_on`, fp16-Fast-Kopie 1.14 GB, Spans identisch (max. Konfidenz-Abweichung 0.015 gegen fp32-Original). (g) Die Zeile `Gewichte: <dtype> auf <device>` (emittiert in `run_ner` NACH `_load_tagger`, nie in `_timed_load` — dort gälte jeder Fehler als kaputte Fast-Kopie) ist ein Contract mit dem Smoke-Check `ner precision`: mit MPS muss sie `torch.float16 auf mps` lauten, sonst ist der Fix still verloren (auf Dev-Macs unsichtbar).
- **`diarize.py` übergibt pyannote eine vorgeladene 16-kHz-Waveform, nie den Dateipfad (Issue #141).** Mit Pfad schneidet pyannote jeden Embedding-Chunk (~3000 bei 50 min) einzeln über den torchcodec-Shim von der Platte und resampelt ihn 48 → 16 kHz. Die Waveform muss schon in der Ziel-Rate (`pipeline._audio.sample_rate`) vorliegen, sonst resampelt `Audio.crop` weiter pro Chunk. `load_waveform` liest und resampelt **blockweise** (`BLOCK_SECONDS`): `torchaudio.functional.resample` am Stück entfaltet die ganze Datei per conv1d/im2col — 19 GiB Zuwachs für 2 h, der alte Pfad-Aufruf tat intern genau das (gemessen 5.4–8.4 GB Peak-RSS bei 28–45 min, blockweise 1.7 GB). Smoke-Check `diarize waveform preload` failt, wenn diarize.py still auf den Pfad zurückfällt — z. B. nach einem pyannote-Update ohne `_audio`, oder wenn Segmentierungs- und Embedding-Rate abweichen (dann resampelte die Segmentierung die vorgeladene Waveform wieder am Stück). `diarize waveform blocks` vergleicht `load_waveform` über mehrere Blockgrenzen mit torchaudio am Stück; der Block-Kontext kommt aus `Resample.width` (echter Kernel, nicht nachgebaute Formel), der Kernel in float32 wie bei `functional.resample`.
- **Standalone-Sidecar wird beim Build geprunt** (`build-sidecar.sh`, 1.0 GB → ~684 MB): `__pycache__`, torch-Header, Test-Dirs, pip/setuptools, plus runtime-verifiziert ungenutzte Pakete (grpc, fontTools, sqlalchemy). **Fallen:** (a) `torch/bin/torch_shm_manager` und `torch/testing` müssen bleiben — `import torch` raist sonst; (b) `networkx` sieht import-time ungenutzt aus, wird aber von pyannote LAZY beim Pipeline-Load importiert; (c) jeder Aufruf des Standalone-Python OHNE `PYTHONDONTWRITEBYTECODE=1` regeneriert ~100 MB pyc-Caches (die Sidecar-Spawns und build-sidecar.sh setzen die Var; bei manuellen Aufrufen selbst dran denken — `verify-bundles.sh` schlägt sonst Alarm). Erweiterungen der Prune-Liste brauchen einen End-to-End-Inferenz-Test, nicht nur Import-Checks.
- **Queue-Pause während der Aufnahme:** `TaskQueueService.setRecordingPause(true)` wird in `recording:start` gesetzt und in `stopRecordingInternal()` (VOR dem enqueue) wieder gelöst — deckt manuellen Stop, Auto-Stop und Tray-Stop ab. Der Guard sitzt in `processNext()`, pausiert also zwischen Pipeline-Steps; ein laufender Task läuft aus. Flag ist in-memory → Neustart startet immer unpausiert. Während der Aufnahme enqueue-te Sessions (z. B. PDF-Import) bleiben regulär in `queued` und sind KEINE Orphans (pending Task-Rows existieren).
- **Review-Ungating:** Die Session erreicht `'review'` bereits beim Abschluss der Anonymisierung; die Summarization läuft danach im Hintergrund (SummaryPanel refetcht bei ihrem `task:completed`). `handleTaskFailure` errort für Summarization-Tasks NIE die Session — ein `review→error` würde das fertige Transkript hinter einem Retry verstecken.
- **Summarization output is JSON-Schema-driven, not regex-parsed.** `LlamaSummarizer` passes `--json-schema` to llama-cli; the grammar engine constrains token sampling so the model can ONLY emit `{title, summary}` objects matching the schema. Output shape is defined ONCE in `src/main/ml/summarization-schema.ts` (Zod validator + JSON Schema string side-by-side, kept in sync by a unit test). Do not edit the prompt to demand format — the schema does that. Do not parse stdout with line-anchored regexes — llama-cli's spinner ASCII (`\r`-overwrites like `|-\|/-\|/`) prefixes the model's output line in non-terminal stdout capture and breaks anchored regexes; we now `extractFirstJSONObject(stdout)` + `JSON.parse` + Zod-validate.
- **Summarization is OPTIONAL and graceful-skip on any failure.** `SummarizationExecutor` wraps `summarize()` in try/catch and logs + returns cleanly on ANY error (subprocess crash, abort, JSON-extraction failure, schema-validation failure, transient model error). Sessions reach `'review'` regardless of LLM success — `sessions.summary` simply stays `NULL`. Do NOT propagate summarization errors to the TaskQueue: that would set `session.status='error'` and hide the already-anonymized transcript behind a Retry button.
- **Whisper hallucinations on silence are structurally prevented (ADR-007, supersedes ADR-006).** Whisper läuft NICHT mehr auf der vollen WAV, sondern nur auf einer von `AudioStitchService` (`src/main/services/AudioStitchService.ts`) aus den Pyannote-Speech-Segmenten gestitchten WAV mit ±200 ms Padding. Stille-Phasen sind dadurch für Whisper unsichtbar — Halluzinationen wie "Vertraue und glaube, es hilft, es heilt die göttliche Kraft!" oder "Untertitelung des ZDF, 2020" können strukturell nicht mehr entstehen. Output-Timestamps werden über die persistierte `StitchMap` (`src/shared/types/StitchMap.ts`) auf Original-Wall-Clock zurückgemappt, bevor `AlignmentService` läuft — siehe `remapStitchedTimestamp` in `src/main/ml/timestamp-remap.ts`. **Defense in depth:** `-mc 0` (`--max-context 0`) bleibt im `whisper-cli`-Aufruf erhalten und schützt die verbleibenden Speech-Segmente vor Inter-Window-Loops. **Wichtig:** Verwende **nicht** `-nc` / `--no-context` — modernes whisper.cpp lehnt diese Flags ab und exitet **0**, was sich als generischer "no JSON output"-Pfad maskiert. Der exakte Args-Satz ist in `buildWhisperArgs()` (`WhisperService.ts`) und ein Snapshot-Test (`WhisperService.test.ts`) gelockt. Pipeline-Reihenfolge ist single-source-of-truth: backend (`TaskQueueService`) und frontend (`SessionCard`) importieren beide aus `src/shared/constants/pipeline.ts`; ein Snapshot-Test (`src/shared/__tests__/pipeline-order.test.ts`) verhindert lokale Duplikate.
- **Empty-speech recordings reach `review`, not `error`.** Wenn Pyannote auf eine Aufnahme 0 Speech-Segmente meldet (z. B. nur Stille / vergessenes Mikro), produziert `WhisperService` ein leeres `TranscriptData`. `AlignmentService` und `AnonymizationService` haben einen Empty-Path-Shortcut: leeres aligned-Transkript bzw. minimales TipTap-Doc `{type: 'doc', content: [{type: 'paragraph'}]}` — die Session erreicht regulär den Review-Editor. Erfolgskriterium #2 in Issue #78. Achtung beim Editieren der beiden Services: bei leerem Input NICHT throwen, sonst landet die Session in `'error'`-State.

- **Clipboard export:** Anonymized text can be exported to clipboard from Review Editor (toast confirmation)
