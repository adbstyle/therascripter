# Patient Dossiers

Story #204 (Epic #192). A patient dossier holds the master data and health information of one patient: first and last name (required), patient dossier ID, birth date, diagnoses, medication and a free note. Sessions and PDF documents are assigned to dossiers and shown in the dossier's timeline (#205, section «Assignment, timeline and document date»). Later stories take them along when a dossier is deleted (#207), start recordings and imports from a dossier (#206) and list recently opened dossiers (#213).

This page describes the backend (main process, shared code, preload) and the user interface (renderer).

## Storage

- Only local, in the SQLite database `~/.therascript/data/therascript.db`, table `dossiers` (migration 020). A dossier is stored as soon as first and last name are given.
- Kept without time limit until the user deletes it or removes Therascript completely. Updates of the app keep every dossier (migration 020 only adds tables and a column).
- Not pseudonymized and not hidden in the pseudonymized view (#204 OOS 1/5). Protection is the same as for the other app data: the FileVault warning at startup.
- Details of the table, the equality rule and the deletion: [storage.md](../architecture/storage.md) («`dossiers`», «Deleting a patient dossier»).

## Rules

| Rule | Where |
|---|---|
| First and last name required; whitespace and invisible characters (U+200B–U+200D, U+FEFF) only count as empty, invisible characters are removed and ignored for equality (AK 2) | `DossierNameSchema` (`src/shared/validation/dossier-schemas.ts`), `DossierService` |
| Names and dossier IDs are equal when they differ only in case, leading/trailing whitespace or umlaut spelling — «Müller» = « mueller » = «MÜLLER», decomposed input (NFD) included (AK 7) | `normalizeDossierKey` (`src/shared/utils/dossier-normalize.ts`), stored in the `*_norm` columns |
| A dossier ID another dossier already has is rejected — on create and on update; the answer names the owner (AK 5) | `DossierService.create/update` → `external-id-taken`; partial unique index as backstop for concurrent requests |
| An empty dossier ID means «no ID»; any number of dossiers may have none | `cleanExternalId` in `DossierService` |
| Same first and last name: `create` answers `duplicate-name` with the other dossiers and creates the dossier when called again with `confirmDuplicate: true`; `update` saves and returns the other dossiers in `duplicates` (AK 6) | `DossierService` |
| Birth date: complete, valid calendar day (29.02. only in leap years, no 31.04.), from 1900 on (typo guard, «Bitte ein Datum ab 1900 eingeben.»), not after today in the Mac's local time (AK 8) | `PastOrTodayIsoDateSchema`, `isValidIsoDateNotAfter` / `localTodayIso` / `parseSwissDate` (`src/shared/utils/calendar-date.ts`); stored as `YYYY-MM-DD` |
| Diagnoses, medication and note: multi-line free text up to 20 000 characters each (AK 4) | `DossierFreeTextSchema`, table CHECKs |
| Control characters (U+0000–U+001F, U+007F) are rejected in names and dossier ID; in free text only line break (LF, CR) and tab are allowed | `hasControlChars` / `hasControlCharsExceptLineBreaks` in the schemas and in `DossierService` |
| Changes are saved per field (autosave, AK 10); a rejected change saves nothing of that patch | `dossier:update` with a single-field patch |
| The overview is sorted by last name, then first name, ä as ae (AK 12), and shows the number of entries and the day of the latest entry; it carries no diagnoses, medication or note | `DossierRepository.listSummaries` |
| 500 dossiers are listed without noticeable delay (AK 15) | test with 500 rows in `DossierService.test.ts` (budget 1 s — generous so slow CI machines do not flake) |

## Deleting

`dossier:deletePreview` returns what a deletion takes along; `dossier:delete` deletes only if the preview the user confirmed still matches (fingerprint). Sessions assigned only to this dossier are deleted with it via the session deletion of #202; sessions also assigned to another dossier stay. While an exclusively assigned session is being recorded, deleting is refused. The dossier row is deleted with `secure_delete` and followed by a WAL checkpoint, so it is neither findable nor recoverable in the app's files (#204 PC 4); an interrupted deletion of the sessions is completed at the next start (PC 5). Sequence: [storage.md](../architecture/storage.md) «Deleting a patient dossier».

Both confirmation dialogs of «TheraScript vollständig entfernen» — the in-app `ConfirmDialog` in `AboutPage.tsx` and the native one in `system-handlers.ts` — list «Alle Patientendossiers (Stammdaten, Diagnosen, Medikation, Notizen)» (AK 18).

## Assignment, timeline and document date (#205)

Sessions and PDF documents can be assigned to one or more dossiers and unassigned again at any time — in every state, also while recording, while processing and after an error (AK 1–3). Unassigned contents stay fully usable (AK 4). Assigning or unassigning changes neither text, pseudonymization, title nor summary (PC 2). Assigning and setting the document date also work in the Klartext view: both are metadata of a session, not its content — the read-only rule of the Klartext view (#203 AK 8) protects the text and the pseudonymization, which neither action touches.

| Rule | Where |
|---|---|
| Assign is idempotent (`INSERT OR IGNORE`); a missing session or dossier, or a session being deleted, answers `not-found` and changes nothing (PC 3) | `SessionDossierService.assign` (`src/main/services/SessionDossierService.ts`), `SessionDossierRepository` |
| Unassign deletes the row; with `secure_delete` it is overwritten in the database file, then `wal_checkpoint(TRUNCATE)` empties the WAL (PC 5). The session stays with all contents (PC 1). Deleting a session removes its assignments by cascade (PC 4/5) | `SessionDossierService.unassign`, `walCheckpointTruncate` |
| Every change sends `sessions:changed` and `dossiers:changed` (badges in the list, count and timeline of the dossier) | `ChangeEvents` |
| Timeline order (AK 6/8/9): latest day first; the day of a session is the local day of its recording, the day of a PDF its document date or else the local day of its import; on the same day sessions before PDFs, then by timestamp (recording resp. import) latest first, the id makes the order deterministic | `SessionDossierRepository.timeline` — computed in SQLite with `date(created_at,'localtime')`, returned as `sortDay`; the renderer only groups by month (`utils/groupTimelineByMonth.ts`) and never converts time zones |
| Sessions being deleted (`deleting_at`) appear in no timeline and no list | every query filters `s.deleting_at IS NULL` |
| The session list gets its badges from a second query over all assignments (`listForSessions`, one JSON parameter, no `GROUP_CONCAT`), merged in the main process; `session:list` returns `SessionListItem` (= `Session & {dossiers: DossierRef[]}`) | `SessionDossierService.listSessions` |
| Document date (AK 18–22): only for PDFs, a complete valid calendar day from 1900 on (typo guard, also for the birth date: «Bitte ein Datum ab 1900 eingeben.», `MIN_CALENDAR_YEAR` in `calendar-date.ts`) and not after today (local time); it can be changed but never reset to `NULL` (OOS 3); one value per PDF, the same in every dossier; it does not change the order or grouping of the session list (OOS 4) | `SessionService.setDocumentDate`, `SessionDocumentDateSchema`, `sessions.document_date` |
| Performance (AK 25, NFR 3): 2 000 sessions with badges and a 300-entry timeline | `SessionDossierService.test.ts` (main-process budget 300 ms / 100 ms), `DossierTimeline.test.tsx` (300 entries rendered in jsdom under 1 s) |

## Recording and import from a dossier (#206)

The head of a dossier page offers «PDF importieren» and «Aufnahme starten» (filled `bg-recording-solid`, hidden while a recording runs — there is no second recording); PDFs can also be dropped onto the timeline. All three go through `useWorkspaceActions()` with `{ dossierId, dossierName }`:

- **Recording:** `recording:start` with `{ dossierId }` assigns the new session right after creating it (PC 1). The app stays on the dossier page; the timeline shows the live card, the `ConsentBanner` appears, the `RecordingBar` is hidden there (`useRecordingDossierIds`). The assignment survives every way a recording ends (PC 3). Details: [audio-recording.md](audio-recording.md).
- **Import:** `import:pdf` with `{ dossierId }` assigns each PDF before its processing is enqueued (PC 2). Details: [pdf-import.md](pdf-import.md).
- **Failed assignment (AK 2):** recording and import go on; a 10-second error toast names the recording by its start time («Die Aufnahme vom 14.11.2026, 10:05 läuft, konnte dem Patientendossier «Hofer, Lukas» aber nicht zugeordnet werden. Sie können das in der Liste «Transkriptionen» über «Dossier zuordnen» nachholen.») or every PDF by title (`utils/dossierAssignmentNotice.ts`). The dossier name comes from the page; if unknown, it is looked up and omitted if the dossier no longer exists.
- Outside a dossier nothing asks for a dossier (OOS 1).

Tests: `recording-handlers.dossier.test.ts`, `pdf-handlers.dossier.test.ts` (main), `DossierStartFromDossier.test.tsx`, `DossierTimeline.test.tsx` (drop), `useRecording.test.ts` (renderer).

## Recently opened (#213)

«Zuletzt geöffnet» in the sidebar lists the eight most recently opened dossiers, sessions and PDF documents (table `recent_items`, survives restarts). Saved when a dossier or session page opens and when a recording starts (also from a dossier); imported PDFs are not added — they were not opened. The running recording always comes first. Each entry shows its kind as an icon with an accessible name and its name in the chosen view (dossier names are not hidden by the pseudonymized view, Epic OOS 16). Deleted dossiers, sessions and PDFs disappear at once — also while the physical deletion of a session still runs — and their rows are gone from the files (PC 2). Back and forward (‹ ›, ⌘[ / ⌘]) walk the pages visited in this run; deleted objects leave that history immediately (PC 3), the history is not kept across restarts (OOS 1). Details: [overview.md](../architecture/overview.md) «Navigation», [storage.md](../architecture/storage.md) «`recent_items`», [ipc-api.md](../architecture/ipc-api.md) «Recent Handlers».
